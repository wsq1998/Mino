## 1. 现状盘点（已核实到行号）

### 1.1 中转站（F10）

| 项 | 现状 |
|---|---|
| 核心 | `main/core/stash.js` 已完整实现 |
| 机制 | **只存路径引用**，不移动/复制/删除源文件；`add` 时 `fs.statSync` 校验存在性 |
| 上限 | `MAX_ITEMS = 100` |
| 落盘 | `userData/mio-stash.json`（`stash.js:13`） |
| 数据 | `{ id, path, name, size, isDir, addedAt }` |
| 列表 | `list()` 实时 `statSync` 刷新 `exists`/`size`，源文件被删则标 `exists:false` |
| UI | `index.html:143-150`，位于**常用页**：粘贴路径输入框 + 列表 + 清空按钮 |
| 渲染 | `app.js:691-737`（`renderStashCard` / `addStash` / `clearStash` / 事件委托删除） |
| 开关 | `swStash`（`index.html:600`，`app.js:2625`） |
| IPC | `v2-stash-list` / `-add` / `-remove` / `-clear`（`main.js:3396-3409`） |

**诊断**：能力只有「进」和「删」，没有「用」。

1. **投递入口单一** —— 只能手动粘贴路径。真实场景是"我在某个 App 里看到一个文件，想先丢过去"，复制路径 → 切窗口 → 粘贴 → 回车，四步。
2. **存进去之后无事可做** —— 没有打开、没有在访达中显示、没有复制路径、没有移动到目标目录。中转站成了只进不出的仓库。
3. **无组织维度** —— 100 项平铺，没有时间分组、没有备注、没有置顶。
4. **不能从系统直接投递** —— 无拖拽、无「选择文件」面板、无访达右键/服务入口。

### 1.2 磁盘太阳图（F12）

| 项 | 现状 |
|---|---|
| 核心 | `main/core/sunburst.js` |
| 扫描 | `/usr/bin/du -sk -d {depth-1}`，`timeout 30s`，可 `cancel()` |
| 范围 | **仅 `~/` 下 7 个目录**：Desktop / Documents / Downloads / Movies / Music / Pictures / Applications（`sunburst.js:12-14`） |
| 深度 | `depth` 参数 1–6，默认 2（`sunburst.js:77`） |
| 缓存 | 10 分钟（`CACHE_TTL_MS`，`sunburst.js:11`） |
| 纯函数 | `parseDu(out, root)`（`sunburst.js:23`）、`computeOwnSize(node)`（`sunburst.js:59`）—— **可单测，本次升级应保留并扩展** |
| UI | `index.html:349-356`，位于**状态页**：`<canvas width="260" height="260">` + 图例 + 重新扫描按钮 |
| 绘制 | `app.js:849-890` `drawSunburst()` —— **单层饼图**（只画 `tree.children` 一层，`ctx.arc` 实心扇形） |

**诊断**：名不副实。

1. **不是太阳图，是饼图** —— 真正的 sunburst 是多层同心环，一眼看出"哪一层吃掉空间"。当前只有一层（`app.js:858-884` 只遍历 `tree.children`）。
2. **范围太小，恰好漏掉用户最关心的部分** —— 只扫 `~/` 七目录，**看不到 `~/Library`**（用户系统数据膨胀的主场所）、看不到 `/Applications`、`/System`、其他卷。
3. **不可交互** —— canvas 死图，无 hover、无点击下钻、无跳转。
4. **没有 drill-down** —— 看到 Documents 占 30GB，想进去看是哪个子目录，做不到。
5. **进度是假的** —— `app.js`/`sunburst.js:95-99` 用"已执行时长 ÷ 100"近似，注释亦承认（`sunburst.js:95`）。

## 2. 方案一：中转站

### 2.1 定位重述

**中转站 = 一个临时取件码头**，核心是两段闭环：**投递（in）→ 取用（out）**。
当前实现把"存"做完了，缺的是"投递得爽"和"取用得出"。

### 2.2 能力设计

| 维度 | 设计 | 优先级 |
|---|---|---|
| **投递** | ① **拖拽文件/文件夹到卡片**（`dragover/drop`）② 「选择文件…」系统面板（`dialog.showOpenDialog`，支持多选）③ 粘贴路径（保留现有）④ 从剪贴板历史一键转入 | P0（①③）、P1（②④） |
| **组织** | 按「今天 / 更早」自动分组；`pin` 置顶；`memo` 一行备注（如"待报销"） | P1 |
| **取用** | 每项菜单：在访达中显示 / 用默认 App 打开 / 复制路径 / 移除引用 | **P0** |
| **批量取用** | 多选 → 批量「移动到…」「复制到…」 | P1 |
| **持久化** | 沿用 `mio-stash.json`，`item` 新增 `pin` / `memo` 字段（向后兼容，旧项读取时补默认值） | P0 |

### 2.3 安全约束（必须保持）

- **默认仍然只存引用** —— 投递动作不发生任何文件搬移。
- **「移动/复制到…」是新增的显式动作**：
  - 必须**二次确认**（复用现有 `showConfirm`）
  - 目标目录必须通过校验：`path.isAbsolute` 且**不得命中** `clean/targets.isBlacklistedPath()` 的黑名单语义（系统目录、`/Library/Compo...》、钥匙串等）
  - 移动实现禁止 `rm` —— 跨卷用 `fs.renameSync` 失败时降级为 `copyFile + shell.trashItem`（**绝不 unlink**）
- 目标目录选择走 `dialog.showOpenDialog({ properties: ['openDirectory', 'createDirectory'] })`，不让渲染层传任意路径。

### 2.4 视觉（对齐 iOS 液态玻璃）

- 列表行：半透明玻璃行 + 1px 高光描边；hover 时轻微上浮。
- 拖拽态：整卡高亮 + 内描边扩散，投放区显示虚线框。
- 空态：不显示"暂无数据"，显示引导语 + 一个虚线投放框。

## 3. 方案二：磁盘太阳图

### 3.1 定位重述

从**「一张死饼图」**升级为**「可下钻的层级空间地图」**。

### 3.2 数据范围（三档）

| 档位 | 覆盖 | 耗时 | 门槛 |
|---|---|---|---|
| 快速 | `~/` 七大目录（现状） | 秒级 | 无 |
| 标准（**默认**） | `~/` + `~/Library` + `/Applications` | 十秒级 | `~/Library` 需**完全磁盘访问** |
| 全盘 | 上述 + `/System` + `/private/var` + 其他卷 | 数十秒 | 同上；部分目录 SIP 保护只读 |

### 3.3 交互设计

| 交互 | 行为 |
|---|---|
| 悬停扇区 | 高亮该扇区 + 高亮其**祖先路径**；中心圆显示「路径 · 大小 · 占比」 |
| 点击扇区 | **下钻** —— 该节点成为新的中心，内环重绘为其子目录 |
| 面包屑 | `Macintosh HD › Users › kaven › Documents`，点击任一级返回 |
| 右键扇区 | 「在访达中显示」/「复制路径」 |
| 中央留白 | 显示当前焦点目录名 + 大小（不是装饰） |

### 3.4 渲染技术选型

**保持 canvas，不引入图表库**（硬约束：零第三方运行时依赖）。

理由：太阳图的绘制量很小（几百个扇区），canvas 2D 足够；引入 d3 / echarts 会破坏 `dependencies: []` 的约束。

实现要点：

- 用 `Path2D` 构建扇区，命中测试用**极坐标反算**（`atan2` + 半径区间），比 `isPointInPath` 遍历更快。
- 保留并扩展 `computeOwnSize`：多层环需要每层各自的"自身大小"（`own`），现有实现已算好，可直接复用。
- 深色主题适配：颜色从主题变量取色阶，同一父级下用**同色系不同明度**，一眼看出归属。

### 3.5 扫描引擎改进

- 现有 `du -d (depth-1)` 一次只能扫一个 root。多层环需要**同一棵树的多层数据** → 改为 `du -sk -d {depth}` 一次拿到 `depth` 层，`parseDu` 已支持任意层（只是之前只传了 1）。
- **进度改诚实**：无法从 `du` 拿真实进度，就不要假装。改为「扫描中… 已耗时 8s」（或按已知顶层目录数分批 spawn 多个 `du`，逐批完成 → 真实进度）。
- **权限降级**：`~/Library` 被 TCC 挡住时（**与 `.Trash` 被 EPERM 挡住是同一类问题**，见记忆中的废纸篓 bug），该节点标注「需要完全磁盘访问」并给系统设置深链，而不是静默显示 0。

### 3.6 APFS 口径问题（必须处理）

`du` 统计的是**逻辑大小**，与访达「已用」不一致的原因：APFS 容器多卷共享空间、快照、克隆文件、稀疏文件。

处理方式：**以 `df` 的已用量为基准**，`du` 只用于**相对占比**。UI 上明确标注"相对占比，非精确值"，避免用户拿它跟访达对不上账而质疑数据造假。

## 4. 方案三：清理页顶部磁盘总览模块

### 4.1 布局

见对话中的设计稿。结构：

```
磁盘总览 · Macintosh HD                    2 分钟前扫描
238 GB 可用 / 494 GB                        已用 51.8%
[████████████ 分段着色容量条 ████████████]
──────────────────────────────────────────
■ 用户目录    /Users/kaven      142 GB  28.7%  ↗
■ 系统数据    聚合推测值         65 GB  13.2%  ⓘ
■ 应用程序    /Applications      38 GB   7.7%  ↗
■ 系统        /System            11 GB   2.2%  ↗
□ 可用空间                      238 GB  48.2%
                          [重新扫描]
```

**关键设计点：容量条与列表共用同一套颜色** —— 容量条就是把太阳图**线性化**，用户扫一眼就知道"紫色那段是什么"。这条容量条本身就承担了"占比可视化"的职责，列表行则承担"精确数字 + 跳转入口"。

### 4.2 数据来源（两层，先快后慢）

| 层 | 手段 | 时机 | 耗时 |
|---|---|---|---|
| 第 1 层 | `df -k /`（复用 `main.js:354` `diskInfo()`） | 进入清理页**立即**显示 | < 100ms |
| 第 2 层 | 顶层目录 `du -sk -d 0`，与太阳图**共用引擎** | 展开时异步触发，骨架屏占位 | 5–15s |

第 1 层保证"一进页面就有东西看"，第 2 层是增量补充。**不做全屏 loading。**

### 4.3 「系统数据」这一项怎么算

macOS 的「系统数据」不是一个真实目录，是访达的聚合概念（快照、缓存、日志、`/private/var` 等杂项）。

本模块的算法：

```
系统数据 = df 已用总量 − (用户目录 + 应用程序 + 系统 已知目录之和)
```

**必须标注为「聚合推测值」**，且**不提供跳转**（没有对应目录可跳），点击 ⓘ 展开解释这是怎么算出来的。

> 这一项正是用户上次"系统数据 70+GB 找不到元凶"的答案所在 —— 它该是模块里**最醒目**的一行，而不是被藏起来。

### 4.4 点击跳转访达（本模块的核心新增能力）

**现状：没有通用能力。** 全项目只有一处硬编码的 `shell.showItemInFolder`，用于打开 `userData/mio-state.json`（`main.js:1267`）。

需新增 IPC：

```
v2-reveal-path  { path }  →  { ok, error? }
```

行为：
- 目录 → `shell.openPath(dir)`（打开该目录）
- 文件 → `shell.showItemInFolder(file)`（在父目录中选中）

**安全校验（不可省）**：

1. 路径必须**来自主进程扫描结果的缓存**，不接受渲染层任意传入 —— 渲染层只传**节点 id**，主进程查表还原路径。这从根上杜绝了路径注入。
2. 兜底再做一次白名单校验：仅允许 `/Applications`、`/System`、`/Library`、`/Users/<me>/**`、`/private/var`、`/Volumes/**` 前缀。
3. `/System`、`/private/var` 等受 SIP 保护的路径，`openPath` 可能被系统拒绝 → **捕获失败并提示**"该目录受系统保护，无法在访达中打开"，不要静默失败。

## 5. 三者关系与数据流

```
                    ┌─────────────────────┐
                    │  df -k /  （秒出）    │
                    └──────────┬──────────┘
                               │ total / avail / usedPct
                               ▼
        ┌──────────────────────────────────────────┐
        │   清理页 · 磁盘总览卡（新增）              │
        │   容量条 + 占比列表 + 点击跳访达            │
        └──────────────┬───────────────────────────┘
                       │ 展开 / 点「分析」
                       ▼
        ┌──────────────────────────────────────────┐
        │  sunburst.js 扫描引擎（复用 + 扩展）       │
        │  du 多层扫描 · 缓存 · 可中止 · 权限降级     │
        └──────────────┬───────────────────────────┘
                       │ 同一棵树
              ┌────────┴────────┐
              ▼                 ▼
      ┌──────────────┐  ┌──────────────┐
      │ 太阳图（多层环）│  │ 中转站        │
      │ 下钻 · 定位    │  │ 投递 · 取用   │
      └──────────────┘  └──────────────┘
              └────────┬────────┘
                       ▼
              同一个 reveal-path IPC
```

**关键决策：三个功能共用一套扫描引擎和一套跳转 IPC。** 不重复造。

太阳图与总览卡的关系，两种选择：

- **方案 A（推荐）**：总览卡展开后**内嵌太阳图**，占位同一个模块。清理页顶部一个卡片解决"看 → 分析 → 去处理"。
- **方案 B**：总览卡只管容量与占比列表，太阳图独立成卡放在下面（或留在状态页）。

方案 A 的好处是入口唯一、不重复；代价是该卡变重。**建议 A，但太阳图默认折叠**，不让首屏变慢。

## 6. 需要新增的 IPC 契约

| 通道 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `v2-disk-overview` | — | `{ total, avail, usedPct, isAPFS }` | 复用 `diskInfo()`，秒回 |

所有新增通道都要在 `preload.js` 的 `v2` 命名空间下暴露，保持现有风格。

## 7. 安全与边界（汇总）

| 风险 | 处置 |
|---|---|
| 路径注入 | reveal/move 只收节点 id，主进程查表还原 |
| 误删 | 全项目唯一删除通道 `shell.trashItem`；移动跨卷降级不用 unlink |
| TCC 权限 | `~/Library`、`.Trash` 需完全磁盘访问 → 缺失时降级提示 + 系统设置深链，不静默显示 0 |
| APFS 口径 | `du` 只用于相对占比，标注"非精确值"；`df` 为准 |
| 扫描卡顿 | 后台 spawn + 可中止 + 诚实进度；不用"假进度条" |
| 零依赖 | 不引入 d3/echarts，canvas 手绘 |
| 性能 | 10min 缓存保留；进入清理页只跑 `df`，`du` 必须用户展开才触发 |

## 8. 分期实施建议

| 期 | 内容 | 依赖 |
|---|---|---|
| **P0** | ① `v2-reveal-path` + 路径白名单 ② 清理页磁盘总览卡（df 层 + 占比列表 + 跳转）③ 中转站「取用」动作（访达/打开/复制路径） | 无，可立即开工 |

## 9. 待用户确认的问题

1. **太阳图数据范围默认哪一档？** 标准档要读 `~/Library`，首次会弹完全磁盘访问授权，是否接受？
2. **总览卡与太阳图合并（方案 A）还是分开（方案 B）？**
3. **中转站要不要支持"移动到指定目录"？** 这会突破"只存引用、绝不碰源文件"的现有约束，属于新增风险面。若不要，可只保留"在访达中显示 + 复制路径"。
4. **太阳图最终住哪？** 状态页（现状）／清理页／两处都放（需处理数据一致性）。
5. **清理页总览模块是否需要"一键交给清理流程"**（如点击「系统数据」行直接跳到对应清理项）？
